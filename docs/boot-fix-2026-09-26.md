# First hardware boot failure: diagnosis and rebuilt image

Board reported by the user: **STM32MP157F-DK2, MB1272 Var4.0 Rev.C-03**.
The original image reached Linux 6.9.8 after TF-A, SP_MIN and U-Boot, then
waited for `/dev/mmcblk0p4`. The subsequent hardware test reported by the user
on 2026-09-28 passed through to the Buildroot login prompt; results are recorded
below. The agent performed no hardware operations.

## Root cause and minimal kernel fix

Inspected `/var/cache/astro-clock/output/build/linux-6.9.8/.config` before
reconfiguration. `CONFIG_I2C` was disabled. The upstream C-DK2 `linux.config`
requests the STM32 I2C and STPMIC1 drivers but does not explicitly enable I2C.
Linux `drivers/gpu/drm/Kconfig` selects I2C; disabling DRM in the minimal
fragment removed that implicit selection. Kconfig consequently dropped the
I2C controller, STPMIC1 MFD and STPMIC1 regulator drivers.

The SDMMC device at `58005000` requires the PMIC's buck4 (`v3v3`). Without the
PMIC driver, its regulator supplier never probes, explaining the reported
supplier wait and absent root block device. This is not an ext4 or partition
number failure.

The only functional addition to `linux-minimal.fragment` is `CONFIG_I2C=y`.
Existing upstream driver requests then resolve correctly; no generated config
was edited manually.

| Kernel option | Before | Rebuilt | Relevant dependency |
| --- | --- | --- | --- |
| CONFIG_I2C | n | y | selects RT_MUTEXES, IRQ_DOMAIN |
| CONFIG_I2C_STM32F7 | absent | y | I2C menu, ARCH_STM32; selects I2C_SLAVE/I2C_SMBUS |
| CONFIG_MFD_STPMIC1 | absent | y | I2C=y and OF; selects REGMAP_I2C, REGMAP_IRQ, MFD_CORE |
| CONFIG_REGULATOR | y | y | regulator framework |
| CONFIG_REGULATOR_STPMIC1 | absent | y | MFD_STPMIC1 and regulator menu |
| CONFIG_MMC | y | y | MMC framework |
| CONFIG_MMC_ARMMMCI | y | y | ARM_AMBA |
| CONFIG_MMC_STM32_SDMMC | y | y | MMC_ARMMMCI; defaults y |
| CONFIG_EXT4_FS | y | y | block filesystem; selects JBD2, CRC16, CRYPTO_CRC32C, etc. |

Pinctrl (`PINCTRL_STM32MP157`), clocks (`COMMON_CLK_STM32MP157`), MMC block,
GPT (`EFI_PARTITION`), AMBA and OF remained built in. No storage, pinctrl,
clock or filesystem option was directly disabled by the minimal fragment.
All nine requested options and the boot-critical dependencies were checked
in the rebuilt config. The config extracted from the rebuilt zImage matches
the effective `.config` byte for byte.

## F-DK2 migration and limits

The pinned Buildroot 2025.02.18 commit remains
`d030e36bbc9669230c015be971b14b6e062cfdde`; its source checksum remains in README.
Inspected the actual extracted Linux 6.9.8, U-Boot 2024.07 and TF-A v2.9 trees:

- Linux `arch/arm/boot/dts/st/` has C-DK2, but no F-DK2 board DTS.
- U-Boot `arch/arm/dts/` and its upstream DTS subtree likewise lack F-DK2.
- TF-A `fdts/` has `stm32mp157f-dk2-fw-config.dts` (512 MiB DDR), but no
  `stm32mp157f-dk2.dts` board source.
- Buildroot has the C-DK2 baseline and supports custom Linux, U-Boot and TF-A
  DTS inputs. There is no native F-DK2 defconfig in this pin.

Therefore merely changing in-tree DTB names would fail. External, explicitly
local compatibility DTS files include each pinned component's existing C-DK2
board source and override the model and primary compatible for F-DK2. This is
**not a native upstream F-DK2 backport**. It retains the existing SP_MIN boot
architecture and conservative DK2 wiring/clock setup. Later upstream F-DK2
support includes SCMI and further board differences; see the
[upstream submission](https://lkml.rescloud.iu.edu/hypermail/linux/kernel/2505.3/02342.html).
Display, touchscreen, wireless and audio remain outside this milestone.

U-Boot additionally needs `CONFIG_DEFAULT_DEVICE_TREE` and `CONFIG_OF_LIST`
set to the custom target so its `arch-dtbs` rule builds it. The first rebuild
with only `DEVICE_TREE=` exposed this and failed before image generation;
`uboot.fragment` fixes it. Its U-Boot-only DTS include retains a secondary
`st,stm32mp157c-dk2` compatible because the pinned `board_is_stm32mp15x_dk2()`
uses that value for DK2 setup. Linux and TF-A use F-DK2 as primary compatible.

**650 MHz remains intentional:** TF-A's pinned `stm32mp15xx-dkx.dtsi` programs
PLL1 for 650 MHz (`cfg = <2 80 0 0 0 PQR(1,0,0)>`, `frac = <0x800>`).
This change does not introduce an unverified 800 MHz PLL/voltage configuration.
Native F-DK2 support and 800 MHz operation require a separately validated
platform update. Renaming the model alone does not change the CPU clock.

## Completed hardware test — reported 2026-09-28

**PASS — hardware boot and U-Boot UMS.** The user verified the following on the
actual **STM32MP157F-DK2, MB1272 Var4.0 Rev.C-03**. These are user-reported
hardware results, distinct from the agent's earlier static and host image checks.

- TF-A, U-Boot and Linux identify the board as STM32MP157F-DK2.
- U-Boot UMS successfully exposed the SD card and was used to flash it.
- STM32F7 I2C and STPMIC1 initialized successfully.
- `mmcblk0` and partitions `p1` through `p4` were detected.
- `/dev/mmcblk0p4` was mounted as ext4 and remounted read-write.
- The Buildroot login prompt was reached.
- The root filesystem reports `/dev/root / ext4 rw,relatime`.
- Ethernet `eth0` was created but showed `NO-CARRIER`; the physical Ethernet
  link was not tested. Ethernet connectivity remains unverified.

Verified kernel command line:

```text
console=ttySTM0,115200 root=/dev/mmcblk0p4 rootwait
```

These results confirm that the I2C/PMIC fix resolves the original root-device
wait on the tested board. The intentional C-DK2 compatibility reuse and 650 MHz
configuration described above remain unchanged. Physical Ethernet link and
connectivity testing are still required; no 800 MHz verification is claimed.
